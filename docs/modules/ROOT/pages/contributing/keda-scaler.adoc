= Developing KEDA scaler mappings

Camel K can derive KEDA triggers from the consumer endpoints of an Integration.
This page explains how to extend that discovery with a mapping for another Camel component.
For information about configuring autoscaling, see the xref:scaling/integration.adoc[Integration scaling] guide and the xref:traits:keda.adoc[KEDA trait] reference.

NOTE: A scaler mapping translates a Camel component URI into metadata for an existing KEDA scaler.
It does not implement a new scaler in the KEDA project.

== How automatic discovery works

When the KEDA trait is enabled, `kedaTrait.Configure` runs automatic discovery unless `keda.auto` is set to `false`.
Discovery follows this flow:

. `metadata.ExtractAll` inspects all Integration sources and extracts their Camel `from` URIs.
. Each URI is passed to `MapToKedaTrigger`.
. `ParseComponentURI` separates the URI into its component name, path value, and query parameters.
. The component name is used to look up a `ScaleMapper` in the registry.
. If a mapper is registered, it converts the path and parameters into a KEDA scaler type and metadata, which become a `KedaTrigger`.
. The KEDA trait adds the trigger to the `ScaledObject` that it creates in `Apply`.

An unsupported Camel component has no registered mapper, so it does not produce an automatically discovered trigger.
A manually configured trigger takes precedence over an automatically discovered trigger of the same type.
The trait also merges entries from `keda.autoMetadata` into discovered metadata.

== The `ScaleMapper` registry

The registry and interface are defined in `pkg/trait/keda/mapper.go`:

[source,go]
----
type ScaleMapper interface {
	Component() string
	Map(pathValue string, params map[string]string) (kedaType string, metadata map[string]string)
}
----

`Component` returns the Camel component name used as the registry key.
`Map` receives the path part of the Camel URI and its decoded query parameters, and returns the corresponding KEDA scaler type and metadata.

Each implementation registers itself by calling `keda.Register` from an `init` function.
The blank import of `pkg/trait/keda/scalers` in `pkg/trait/keda.go` ensures that these registration functions run when the trait package is loaded.

== Kafka reference implementation

The Kafka mapper in `pkg/trait/keda/scalers/kafka.go` is the reference implementation.
It maps the Camel URI path to the KEDA `topic`, the Camel `brokers` parameter to `bootstrapServers`, and `groupId` to `consumerGroup`.

For example, this Camel source URI:

[source,text]
----
kafka:orders?brokers=broker:9092&groupId=my-group
----

produces this trigger:

[source,yaml]
----
type: kafka
metadata:
  topic: orders
  bootstrapServers: broker:9092
  consumerGroup: my-group
----

Other KEDA Kafka metadata, such as `lagThreshold`, can be supplied through `keda.autoMetadata` when it is not derived from the Camel URI.

== Adding a mapping

. Add `pkg/trait/keda/scalers/<component>.go`.
. Define a type that implements `ScaleMapper`.
. Return the Camel component name from `Component`.
. In `Map`, translate only relevant Camel URI path and parameter values to the metadata expected by the existing KEDA scaler, and return its scaler type.
. Register the mapper with `keda.Register` in an `init` function.
. Add `pkg/trait/keda/scalers/<component>_test.go`.

Keep component-specific conversion in the scaler package.
Shared URI parsing and registry behavior belong in `pkg/trait/keda`.

== Testing a mapping

Use `pkg/trait/keda/scalers/kafka_test.go` as the model for a new mapper's tests.
Cover at least:

* registration under the expected Camel component name;
* conversion of a complete URI;
* conversion when optional URI values are absent;
* exact KEDA scaler type and metadata keys; and
* `MapToKedaTrigger` behavior for the new component.

If the change affects discovery or trigger precedence, add coverage to `pkg/trait/keda_test.go` as well.
Run the focused tests with:

[source,console]
----
$ go test ./pkg/trait/keda/... ./pkg/trait
----
